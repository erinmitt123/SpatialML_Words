## Differences from B
- Model target: the script defaults to **GPU**, but the imported package is currently built with `--target cpu` (GPU and NPU both fail on Swan, see below). CPU runs ~2.5–3 s per frame, so it only proves the pipeline loads; it is too slow for labels.
- App id `com.wordworld.app`, product name `WordWorld` (the samples app is not overwritten).
- Only the 37 household classes from CLAUDE.md are tracked; others are shown greyed in the debug panel and ignored.
- Coordinates: OpenXR right-handed → Unity by negating z.

## Blockers found on Swan (2026-10-29)
- **YOLOX-M on GPU:** the model compiles (465/465 nodes delegated), then the SecureMR server logs
  `LiteRt create input buffer failed` → `OperatorRunModelInference Unable to initialize LiteRT model and runtime`.
  The NPU fails as well. A CPU build (`--target cpu`) is used only to test the rest of the chain.
- **Room mesh in Spatial mode:** with `PICO_MS_SDK`, `PXR_Loader` creates the "PICO Mesh" subsystem
  only under `AR_FOUNDATION_6` with `arFoundation` on. AR Foundation is not in the project, and SPATIALML_SETUP.md
  says not to guess a version. `RoomMesh` tries the descriptor's `Create()` directly, but it returns null.
  Ask PICO: which AR Foundation version (if any) is supported, or how Spatial-mode apps should get mesh updates.

## Open questions
1. **Colour order.** B feeds RGB 0–255 with no normalisation; YOLOX is usually trained on BGR. Check with PICO which their export expects (CLAUDE.md §2 requires this to match).
2. Letterbox: confirm the pipeline letterboxes the 640 input rather than stretching.
3. Does the frame counter persist between runs? The detector handles either case.
4. Runtime-created meshes may not render in Spatial mode, so the room mesh debug view is best-effort (colliders work regardless).
5. Spatial anchors in Spatial mode: API not yet identified; labels are world-locked without them for now.
6. Licence: the YOLOX-M model is for prototyping only; swap in an Apache-2.0 model before release via `IObjectDetector`.
